### Goal
Pick ready tasks and start a builder session for each, in a fresh worktree at the integration head, up to the worker limit (1 in this milestone).

### Context
`01-architecture.md` §5.2. Settings `workers.max`, `models.builder`.

### Deliverables
- `lib/si/tasks/dispatcher.ex` (`Si.Tasks.Dispatcher`, supervised), `lib/si/tasks/loop_supervisor.ex` (DynamicSupervisor for per-task loops, used in T06.05), `priv/prompts/builder/system.md`, `priv/prompts/builder/task.md`.
- Tests `test/si/tasks/dispatcher_test.exs` (`@tag :pi` for the end-to-end case).

### Specification
- Approval policy guard: while `Si.Profiles.approvals_configured?/0` is false, start no builders. Keep tasks `ready` and create one inbox item (deduplicated): `Choose the builder approval policy: run si init`. The policy is your decision (it belongs to the skipped safety topics); the plan never picks it for you.
- Wake-ups: every 1 s and on `{:task, _, :ready}` broadcasts.
- Capacity: count tasks in `assigned`, `running`, `frozen`, `in_review` that have a live builder session; dispatch while below `workers.max`.
- Selection: ready tasks ordered by `priority` then `inserted_at`.
- For a selected task:
  1. `Si.Worktrees.create(repo, ref: integration head, purpose: :worker, owner: task.id)`; record `worktree_id` and the base on the task.
  2. `Si.Tasks.assign/3` (CAS; on `:stale` skip).
  3. `Si.Sessions.start(role: "builder", profile: "builder", cwd: worktree path, task_id: task.id, model: settings models.builder, extra args: ["--append-system-prompt", builder/system.md path], trust_project: profile.pi.trust_project)`.
  4. `Si.Tasks.start_attempt/2`; start the task's loop process (T06.05) under the loop supervisor.
  5. `Si.Sessions.prompt(session, builder/task.md text)`.
- Session start failure: interrupt the attempt, move the task back to `ready`, retry after 30 s; after 3 failures → `failed` and an inbox item.
- `priv/prompts/builder/system.md` (version 1):
  ```
  You are a builder in Si. You implement exactly one task in this working tree.
  - Start by calling si_task. Work only on that task and stay within its scope; if you must change other files, call si_scope first.
  - Run the task's tests with the commands si_task gives you before reporting.
  - Do not commit, branch or push. Si captures your working tree when you report.
  - When finished, call si_report with status done, a short summary and the test commands you ran.
  - If you cannot continue, call si_report with status blocked and the reason.
  ```
- `priv/prompts/builder/task.md` (version 1): `A task is ready for you. Call si_task to read it, then do it.`

### Tests
- Fake Pi sessions: two ready tasks with `workers.max: 1` → only one assigned; after the first leaves the active states, the second is dispatched.
- Start failure → back to ready with backoff; third failure → failed + inbox item.
- `@tag :pi`: si-faux builder script (`si_task` → `write` file → `si_report` done) → the attempt is reported and the file exists in the task's worktree.

**Expected result.**
- The dispatcher starts builder sessions for ready tasks, up to `workers.max` (1 here), each in a fresh worktree at the integration head.
- It uses the exact builder prompts.
- It retries a failed start with backoff, and starts no builder at all while the approval policy is unset.

**Checks**
1. With `profiles.builder.approvals` unset in a temporary home, add a ready task.
   Expected: no builder starts; exactly one inbox item says `Choose the builder approval policy: run si init`, even after 10 wake-ups.
2. Where the tests set the approval policy.
   Expected: only in their temporary home config, as a placeholder the test chooses. Never in `priv/default_config.yml` or `~/.si/config.yml`.
3. Two ready tasks with `workers.max: 1`.
   Expected: one is assigned; the second is assigned only after the first leaves the active states.
4. Three start failures.
   Expected: 30 s backoff between them (use a fake clock or a shortened interval in the test), then the task is `failed` with an inbox item.
5. `priv/prompts/builder/system.md` and `task.md`.
   Expected: exactly the task's text, as version 1.

**Redo if**
- The dispatcher waits on sessions synchronously inside its callbacks. Rewrite it so that starts run in the per-task loop or a `Task`.
