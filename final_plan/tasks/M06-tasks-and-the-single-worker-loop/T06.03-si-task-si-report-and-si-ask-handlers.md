### Goal
Workers get their task from Si, report back when done or blocked, and can ask questions that land in your inbox.

### Context
`05-schemas-and-config.md` §3 (payloads), `04-protocols.md` §2.4.

### Deliverables
- `lib/si/tasks/tool_handlers.ex` registered for `si_task`, `si_report`, `si_ask` in `Si.Bridge.Tools` at start; tests `test/si/tasks/tool_handlers_test.exs`.

### Specification
- `si_task`: the session's `task_id` → task + repo profile → result per `si_task.result.schema.json`: `task_id`, `attempt` (current attempt n), `round`, `title`, `goal` (= description), `acceptance`, `scope`, `test_paths`, `commands` (`test`, `test_all`, `build`, `lint`, `format` from the profile, placeholders left as-is), `feedback` (the task's `feedback` or null). Session without a task → error `no task assigned`.
- `si_report`: validate; latch with `Si.Tasks.record_report(attempt, args, task.round)`:
  - `:already_reported` → `%{accepted: true, next: "already_reported"}`.
  - `status: "done"` → broadcast `{:attempt_reported, task_id, attempt_id}` on `"task:<id>"` (the loop reacts, T06.05) → `%{accepted: true, next: "checks_started"}`.
  - `status: "blocked"` → task → `blocked`; inbox item `kind: "question"`, title `Worker blocked on <task title>`, body = `blocked_reason` + summary, options `["unblock", "cancel"]`, recommended `unblock` with note text required; → `%{accepted: true, next: "waiting_for_owner"}`. Resolving `unblock` sends the note to the worker as a follow-up and moves the task back to `running` (same attempt); `cancel` cancels the task.
- `si_ask`: inbox item `kind: "question"` (`ref_kind: "session"`), result `%{answer: nil, pending: true, inbox_item_id}`. When resolved, deliver `Answer to your question "<q>": <note>` to the session as a follow-up (`Si.Sessions.prompt(id, text, as: :follow_up)`). (From T12.04 the Lead may answer first.)

### Tests
Handlers with a fake session registered to a task: si_task payload validates against the result schema; report latch; blocked flow creates an inbox item and resolving delivers the note (assert the follow-up via a fake controller); si_ask round trip.

### Acceptance criteria
Tests pass; `bin/ci` passes.

### Verify


**Expected result.**
- `si_task` returns the worker's task in the result schema.
- `si_report` is latched per round and starts the checks, or puts the task on hold as blocked with an inbox question.
- `si_ask` creates an inbox question, and its answer reaches the worker later as a follow-up.

**Checks**
1. The `si_task` result.
   Expected: it validates against `protocol/tools/si_task.result.schema.json`.
2. `si_report` sent twice in the same round.
   Expected: `%{accepted: true, next: "already_reported"}` the second time, and one broadcast.
3. Resolve a blocked item with `unblock` and a note.
   Expected: the worker's fake controller receives the note as a follow-up, and the task is `running` again with the same attempt.
4. A session with no task calls `si_task`.
   Expected: the error `no task assigned`.

**Redo if**
- `si_ask` blocks the tool call until the owner answers. It must answer `pending` at once.
