### Goal
Each role runs with its own Pi agent directory (settings, credentials, Fabric config) and an exact extension set and tool list.

### Context
Pi agent dir files: `settings.json`, `models.json`, `auth.json` (Pi `docs/configuration.md`). `PI_CODING_AGENT_DIR` selects it. Fabric reads `fabric.json` from the agent dir (global) and `.pi/fabric.json` (project); workers ignore project files through `--no-approve` (Pi `docs/security.md`). `01-architecture.md` §6 (Fabric boundary).

### Deliverables
- `lib/si/profiles.ex` (`Si.Profiles`), tests `test/si/profiles_test.exs`.

### Specification
Built-in profile specs (a map in `Si.Profiles`):

| Profile | Extensions | Tools | `fabric.json` |
|---|---|---|---|
| `builder` | fabric, fovea, bridge | Pi defaults | `{"fullCodeMode": true, "agents": {"maxDepth": 0}, "mesh": {"enabled": false}, "capture": {"keepVisible": ["si_task", "si_report", "si_ask", "si_scope", "si_dispute"], "risks": {"si_task": "read", "si_report": "read", "si_ask": "read", "si_scope": "read", "si_dispute": "read"}}, "approvals": <profiles.builder.approvals>}` |
| `reviewer` (Astra, critic, arbiter) | bridge | `read,grep,find,ls,si_verdict,si_ask` | none (Fabric not loaded) |
| `lead` | fovea, bridge | `read,grep,find,ls,si_plan,si_ask,fovea_sketch,fovea_focus,fovea_dwell,fovea_impact` | none |
| `eval_single` | fabric, fovea, bridge (observe mode) | Pi defaults | `{"fullCodeMode": true}` |

Two Pi/Fabric rules shape this table:
- Pi's `--tools` is an allowlist over built-in **and extension** tools (Pi `docs/cli.md`, "-t, --tools"). Every restricted role therefore lists its `si_*` tools and, for the Lead, Fovea's tools; otherwise Astra could not call `si_verdict`.
- In builders, Fabric's full code mode hides tools registered by other extensions from the model unless they are listed in `capture.keepVisible` (Fabric `docs/configuration.md`, "Captured extension tools"). The builder profile keeps the `si_*` tools visible and gives them risk class `read`.

The builder's Fabric `approvals` block (risk classes `read`, `write`, `execute`, `network`, `agent`; policies `allow`, `ask`, `auto`, `deny`) is **your choice**: it belongs to the skipped safety topics, so the plan does not choose it. You set `profiles.builder.approvals` during `si init` (T05.11). Until it is set, the key is absent from `fabric.json`, `approvals_configured?/0` returns false, and the dispatcher (T06.04) refuses to start builders. Any approval dialog that still appears in a headless session goes to your inbox (T05.06).

```elixir
@spec ensure!(String.t()) :: Path.t()        # creates/refreshes $SI_HOME/profiles/<name>, returns the dir
@spec launch_args(String.t(), Si.Toolchains.Toolchain.t(), keyword()) :: [String.t()]
#   opts: trust_project (boolean, from the repo profile), extra_extensions ([path], e.g. si-faux in tests), orchestration_only (boolean)
@spec spec(String.t()) :: map()
@spec approvals_configured?() :: boolean()
```
`ensure!/1`:
- `settings.json`: `{}` (write only if missing; never overwrite your edits).
- `auth.json` and `models.json`: symlink to the files in your Pi agent dir (`Application.get_env(:si, :user_pi_agent_dir, "~/.pi/agent")`) if they exist; never copy credentials.
- `fabric.json`: written from the spec on every call (Si owns it). With `orchestration_only: true` set `fullCodeMode: false` (used from T13.04).
`launch_args/3` returns, in order: `["--no-extensions", "-e", fabric_ext?, "-e", fovea_ext?, "-e", bridge_dir, ...extra_extensions as -e, "--tools", list?, trust_flag]` where `bridge_dir` is `<repo root>/bridge` (resolved from `:code.priv_dir(:si)`'s parent at runtime, or `Application.get_env(:si, :bridge_dir)`), and `trust_flag` is `"--no-approve"` unless `trust_project: true` (then `"--approve"`). Before the bridge exists (T04.03), `bridge_dir` is omitted when the directory is missing.

### Tests
- `ensure!/1` creates the dir, `settings.json` once (a manual edit survives the next call), symlinks when fake user files exist (use a temp `user_pi_agent_dir`), and no links when they don't.
- `fabric.json` content per profile, including `orchestration_only`.
- `launch_args/3` for each profile (exact list), with and without `trust_project` and extra extensions; the reviewer and lead `--tools` lists contain their `si_*` (and Fovea) tool names.
- Builder `fabric.json` contains `capture.keepVisible` and `capture.risks` for the `si_*` tools; the `approvals` key is present only when `profiles.builder.approvals` is set, and `approvals_configured?/0` follows it.

### Acceptance criteria
Tests pass; `bin/ci` passes; no credential file is ever copied (only symlinked).

**Expected result.**

**Checks**
1. Run `h=$(mktemp -d); SI_HOME=$h mix run --no-start -e 'IO.puts Si.Profiles.ensure!("builder")'; ls -la "$h/profiles/builder"`.
   Expected: `auth.json` and `models.json` are symlinks (`->`) into `~/.pi/agent/`, never regular files. Never print what they contain.
2. `jq . "$h/profiles/builder/fabric.json"`.
   Expected: the builder row of the table, with `capture.keepVisible` and `capture.risks` for the five `si_*` tools, and no `approvals` key.

   Expected: the edit is still there.
4. `find ~/.si/profiles -name 'auth.json' -type f 2>/dev/null | wc -l`.
   Expected: `0`.
5. The `eval_single` row.
   Expected: it is part of the profile table in the code and in the tests, like the other rows.

**Redo if**

- `approvals` gets a default value anywhere. Remove it: the owner chooses it (T05.11).
