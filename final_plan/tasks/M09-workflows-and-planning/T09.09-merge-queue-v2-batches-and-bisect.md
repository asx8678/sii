### Goal
Land several queued changes with one test run, and on failure find the change that broke it by bisection, so slow suites don't make the queue a bottleneck.

### Deliverables
Batching in `Si.MergeQueue.Queue`; settings `merge_queue.batch_size` (default 4); tests.

### Specification
- When two or more items are queued, take up to `batch_size` in order; cherry-pick each onto `H` (a conflicting item is ejected, the rest continue); run the landing checks once on the combined result.
- Pass → update the integration ref to the last commit (CAS); all items `landed` with their own commit shas.
- Fail → bisect: test the first half on `H`; if it passes, land it and continue bisecting the second half on the new head; if it fails, bisect within it; a single failing item is ejected. Each check run records its batch id.
- A batch never mixes items whose tasks depend on each other in a way that the dependent was built before the dependency landed (the dispatcher already prevents this; assert it).

### Tests
A batch of 3 good items lands with one check run; a batch of 4 with one bad item ejects exactly that item and lands the others (count check runs ≤ 1 + 2·log2(4)); a conflicting item is ejected without affecting the batch.

### Acceptance criteria
Tests pass; `bin/ci` passes.

**Expected result.** Queued items land in batches of up to `merge_queue.batch_size` with one check run. A failing batch is bisected to eject exactly the item that broke it. A conflicting item is ejected without affecting the rest of the batch.

**Checks**
1. A batch of 3 good items.
   Expected: one check run, and all three `landed` with their own commits.
2. A batch of 4 with one bad item.
   Expected: exactly that item is ejected, the other three land, and there are at most 5 check runs.
3. Batch ids.
   Expected: recorded on every check run.

**Redo if**
- The batch lands partially when its combined check fails. Rewrite it: nothing lands until the bisection has proven each part.
