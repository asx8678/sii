### Goal
Turn an approved plan into tasks ordered by dependencies, give dependent steps to the worker that did the previous step, and handle requests for a wider scope.

### Deliverables
- Build step `for_each: plan.steps`; `si_scope` handler (`lib/si/tasks/scope.ex`); sticky assignment in the dispatcher; settings `workers.sticky_keep_s` (default 600); tests.

### Specification
- Fan-out: one task per plan step: `key` = step id, `title`, `description`, `scope` = `files`, `test_paths`, `acceptance` = the served criteria texts, `depends_on` = task ids of the step's dependencies, tier and review settings from the run; tasks without dependencies are `ready`, others `pending`. `max_parallel` limits concurrently active tasks of this run (the dispatcher counts per run).
- Sticky workers: after a task lands, its builder session is kept idle for `sticky_keep_s` (T06.07 cleanup now skips the session when a dependent task exists). When a dependent becomes ready and `sticky: true`, and the router would pick the same model, assign it to that session: reset its worktree to the new integration head (which contains its landed work), start a new attempt with the same session, prompt `A follow-up task is ready. Call si_task.`.
- `si_scope`: insert `scope_requests` (`pending`); decide:
  - auto-approve when none of the files match `risky_paths`, the request has ≤ 3 files, and the run tier is not `full`;
  - otherwise: the Lead decides (from T12.04); until then an inbox item `kind: "scope"` with options `approve`/`refuse`.
  Reply `%{decision, note}`; `pending` answers are delivered to the worker later as a follow-up. Approved files are appended to the task's `approved_scope` (new column) used by the scope check.

### Tests
Plan with A, B → C: A and B run, C starts after both land; sticky assignment reuses the session and its worktree moves to the new head; scope auto-approve, risky refusal path via inbox, pending answer delivered later.

### Acceptance criteria
Tests pass; `bin/ci` passes.

**Expected result.**
- An approved plan fans out into tasks ordered by their dependencies, with `max_parallel` respected.
- Dependent steps can go to the sticky worker that did the previous step.
- `si_scope` requests are auto-approved or decided, per the rules.

**Checks**
1. A plan with A and B before C.
   Expected: C starts only after A and B have landed.
2. Sticky assignment.
   Expected: the same session is reused, and its worktree is reset to the new integration head.
3. A scope request with 2 non-risky files in a standard run, then with a risky file.
   Expected: the first is approved automatically; the second creates an inbox item.
4. Approved scope.
   Expected: appended to the task's `approved_scope`, so the scope check accepts it.

**Redo if**
- Fan-out creates dependent tasks as `ready`. They must stay `pending` until their dependencies land.
