### Goal
Start runs from a goal with the right amount of process: a tier, a cost estimate that asks you above a threshold, and escalators that raise the tier when risk appears.

### Deliverables
- `lib/si/intake.ex` (`Si.Intake`); CLI `si run "<goal>" [--repo PATH] [--tier T] [--workflow NAME|FILE] [--budget USD]`; settings `budgets.ask_above_usd` (default 10) and `tiers.limits` (`quick.max_diff_lines: 50`, `standard.max_diff_lines: 800`, `max_failed_check_rounds: 3`); tests.

### Specification
- Tier: `--tier`, else the workflow's tier, else `standard`. (Escalators only raise; `quick` must be chosen explicitly.)
- Estimate before starting: the median cost of the last 20 finished runs of the same tier in the same repo (fall back to all repos, then to a fixed default per tier: quick $0.50, standard $3, full $8); after planning, multiply by `steps / median steps` of those runs. Above `ask_above_usd` → inbox approval before the run starts (or before the build step, for the post-plan estimate).
- Escalators (checked on events): a task's diff exceeds the tier's `max_diff_lines`; a task fails checks in `max_failed_check_rounds` consecutive rounds; a scope request is refused; a risky path is touched in a standard run → raise the run tier (`quick → standard → full`), record `run.tier_raised`, and apply the new tier's rules to steps that have not started (e.g. final reviewer, plan gate for re-plans).
- `si run` prints the run id, tier, estimate and the step list, then streams step changes until done (Ctrl-C detaches without stopping the run).

### Tests
Estimate math with fixture runs; approval threshold creates an inbox item; each escalator raises the tier once; CLI output.

**Expected result.**
- `si run` starts a run from a goal. It picks the tier, estimates the cost from the history of past runs, and asks for approval above `budgets.ask_above_usd`.
- Escalators raise the tier once per trigger.
- The command streams step changes until the run ends; Ctrl-C detaches.

**Checks**
1. The estimate math on the fixture runs.
   Expected: the median cost of the last 20 finished runs, the fallback order, and after planning the step-count scaling.
2. Each escalator.
   Expected: the tier is raised once, and `run.tier_raised` is recorded.
3. Ctrl-C during streaming (a test with a killed CLI process).
   Expected: the run keeps going.

**Redo if**
- Escalators can lower the tier. They only raise it.
