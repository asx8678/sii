### Goal
Store bridge events as analytics rows, feed session state to controllers, and stream them to the cockpit.

### Context
`03-data-model.md` §2 (`model_calls`, `turns`, `tool_calls`, `fabric_execs`).

### Deliverables
- Migrations for the four tables; schemas under `lib/si/analytics/`.
- `lib/si/bridge/ingest.ex` (`Si.Bridge.Ingest`); `SessionChannel` `"events"` now calls it.
- Tests `test/si/bridge/ingest_test.exs`.

### Specification
```elixir
@spec handle_batch(String.t(), non_neg_integer(), [map()]) :: {:ok, last_seq :: non_neg_integer()}
```
- The channel keeps `last_seq` in its assigns; events with `seq <= last_seq` are skipped.
- One transaction per batch:
  - `model_call` → insert `model_calls` (`via: "direct"`); `message_end` with `call_id` → update that row's token counts and `cost_usd` (from `usage.cost` when present).
  - `turn_end` → insert `turns`; `tool_end` → insert `tool_calls`; `fabric_exec` → insert `fabric_execs` (from T04.10 events).
  - `agent_start`/`agent_end`/`agent_settled` → for `si` sessions send `{:bridge_event, type}` to the controller (the controller treats them like RPC events, ignoring duplicates); for `user` sessions update `sessions.state` directly with the same transition rules.
- After commit, broadcast `{:bridge_event, session_id, event}` on `"session:<id>"`.
- Unknown event types are counted and ignored.

### Tests
Push batches through `Phoenix.ChannelTest`: rows appear with correct values; a duplicate batch is ignored; usage is joined by `call_id`; controller receives state events; a user session's state changes from agent events.

### Acceptance criteria
Tests pass; `bin/ci` passes.

### Verify

**Expected result.**
- Event batches are stored as `model_calls`, `turns`, `tool_calls` and `fabric_execs` rows, one transaction per batch, skipping batches already seen.
- Usage is joined to calls by `call_id`.
- State events reach controllers, and user sessions' states update directly.
- The cockpit gets broadcasts.

**Checks**
1. Push the same batch twice.
   Expected: one set of rows.
2. A `message_end` whose `call_id` matches an earlier `model_call`.
   Expected: that row's token counts and `cost_usd` are filled in.
3. Measure the time to ingest a 100-event batch.
   Expected: under 50 ms on this machine. Record it. If it is slower, profile before continuing.
4. Look at the ingest code.
   Expected: exactly one `Repo.transaction`/`Si.Events.transaction` per batch.

**Redo if**
- Each event is inserted in its own transaction. Rewrite with one transaction per batch.
