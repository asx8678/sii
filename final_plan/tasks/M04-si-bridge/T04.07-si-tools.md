### Goal
Register the `si_*` tools in Pi (per role), send calls to Si, validate them there, and route them to the context that handles each tool.

### Context
`04-protocols.md` §2.4, `05-schemas-and-config.md` §3. Pi tool definition: `pi.registerTool({name, label, description, parameters: <TypeBox schema>, execute(toolCallId, params, signal, onUpdate, ctx)})`; the result needs `content` and `details`; returning `terminate: true` skips the automatic follow-up (Pi `docs/extensions.md`, "Tools"). Fabric captures registered Pi tools automatically for `fabric_exec`, and in full code mode it hides them from the model unless they are listed in `capture.keepVisible`; the builder profile keeps the `si_*` tools visible (T03.02). Restricted roles list their `si_*` tools in `--tools`, because that allowlist also covers extension tools.

### Deliverables
- `bridge/src/tools.ts` (TypeBox schemas mirroring `protocol/tools/*.args.schema.json`), tests `bridge/test/tools.test.ts`.
- `lib/si/bridge/tools.ex` (`Si.Bridge.Tools`: validation, handler registry, dispatch), tests `test/si/bridge/tools_test.exs`, `@tag :pi` test `test/si/bridge/tools_pi_test.exs`.

### Specification
Bridge:
- Tools per role: builder → `si_task`, `si_report`, `si_ask`, `si_scope`, `si_dispute`; astra/critic/arbiter → `si_verdict`, `si_ask`; lead → `si_plan`, `si_ask`; user → `si_ask`.
- Model-facing descriptions (exact text, they are part of the contract):
  - `si_task`: "Get your current task from Si: goal, acceptance criteria, files in scope, test commands, and feedback from the last round. Call this first."
  - `si_report`: "Tell Si you are finished with this attempt (status done) or cannot continue (status blocked, with the reason). Si then freezes your changes and runs the checks. Call it once, at the end."
  - `si_ask`: "Ask the Lead or the owner a question you cannot answer from the repository. The answer may arrive later as a message."
  - `si_scope`: "Ask for permission to change files outside your task's scope. Give the exact files and the reason."
  - `si_verdict`: "Record your review verdict. Call it exactly once, at the end of the review. Use approve only when there is no blocking finding. Every blocking finding needs evidence: a failing test, a reproduction, a quoted rule, or a concrete input."
  - `si_plan`: "Submit the plan: acceptance criteria and steps with dependencies, files and test paths."
  - `si_dispute`: "Dispute a review finding you believe is wrong, with evidence."
- `execute`: `conn.request("tool", {name, call_id: toolCallId, args: params}, timeoutMs)` with 30 s timeout (`si_ask`: 10 s; Si answers `pending` immediately when it has no answer yet). Reply `{ok: true, result}` → return `{content: [{type: "text", text: <one-line summary of result>}], details: result, terminate}` with `terminate: true` for `si_report`, `si_verdict`, `si_plan`. Reply `{ok: false, error}` or not connected → `throw new Error(error ?? "Si is not connected")`.

Server:
```elixir
@spec register(String.t(), module()) :: :ok          # handler module implements handle_tool(session, name, args) :: {:ok, map()} | {:error, String.t()}
@spec handle(String.t(), String.t(), map()) :: %{ok: boolean(), result: map() | nil, error: String.t() | nil}
```
- Validate args with `Si.Bridge.Protocol.validate({:tool_args, name}, args)`; invalid → `%{ok: false, error: "invalid arguments: <messages>"}`.
- Check the session's role may call the tool (same table); otherwise `error: "tool not allowed for role"`.
- No handler registered → `error: "not_available"`.
- Handlers run in a `Task` under `Si.TaskSupervisor` with the channel replying asynchronously (store `socket_ref`), so slow handlers never block the channel.
- Record event `tool.called` (stream `session:<id>`, data: name, ok) — add `tool.called` to the event catalog.

### Tests
- vitest: tools registered per role; execute returns details and `terminate` correctly; error replies become thrown errors.
- Elixir: validation errors, role check, unregistered tool, a test handler receives args and its result is replied; slow handler (sleep 200 ms) does not block another `events` push on the same channel.
- `@tag :pi`: real Astra-profile session with si-faux script `[{tool_calls: [si_verdict valid args]}]` → a test handler registered for `si_verdict` receives the args; the session reaches idle without another model call (terminate works). A second script with invalid args → the tool result is an error visible in the next step (faux continues with a text step).
