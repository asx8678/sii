### Goal
Upgrade Pi, Fabric or Fovea safely: install a candidate toolchain, run the contract tests against it, review Fabric's new orchestration features against the boundary table, and pin it for new runs only.

### Deliverables
CLI `si upgrade check [--pi V] [--fabric V] [--fovea V]` and `si upgrade pin <toolchain_id>`; `bin/contract-test` accepts `SI_TOOLCHAIN=<id>`; toolchain garbage collection; tests with fake toolchains.

### Specification
- `check`: `Si.Toolchains.ensure/1` for the candidate versions; run `bin/contract-test` with `SI_TOOLCHAIN` set; collect Fabric's changelog entries between the pinned and candidate versions (`node_modules/pi-fabric/CHANGELOG.md` if present); create an inbox item `kind: "approval"` titled `Upgrade to Pi X / Fabric Y / Fovea Z` whose body lists the contract result and the changelog with a checklist: for each new orchestration feature, mark it "on in workers", "shown to Si", or "off in workers" (the boundary table in `01-architecture.md` §6). Options `pin` / `reject`.
- `pin` (or resolving the item with `pin`): only when the contract passed; update `toolchain.*` in `$SI_HOME/config.yml` with the settings writer from T05.11 (it keeps your other keys), record a `compat.yml` entry. Running runs keep their pinned toolchain; new runs use the new one.
- GC: delete toolchain directories not used by any non-terminal run and not current, older than 7 days.

### Tests
Failing contract → cannot pin; passing → pin updates settings and new runs use it while an existing run keeps the old toolchain id; GC keeps in-use toolchains.

### Acceptance criteria
Tests pass; `bin/ci` passes.

**Expected result.**
- `si upgrade check` installs a candidate toolchain, runs the contract tests against it, collects Fabric's changelog, and asks the owner with the boundary checklist.
- `pin` works only after a passing contract run, and affects new runs only.
- Old toolchains are garbage-collected unless something uses them.

**Checks**
1. A failing contract run.
   Expected: `pin` is refused.
2. A passing run, then pin.
   Expected: `toolchain.*` is updated with the settings writer (other keys are kept), new runs use the new id, and a running run keeps the old one.
3. Garbage collection.
   Expected: toolchains used by non-terminal runs, and the current one, are kept.

**Redo if**
- Pinning edits `config.yml` by string replacement. Use `Si.Settings.Writer`.
