### Goal
Make Si usable on your own repositories right after the Astra path: one command that checks and sets up everything, a safe way to change settings from the CLI, the explicit choice of the builder approval policy, and a short user guide.

### Context
`05-schemas-and-config.md` §1 (settings); T03.02 (the builder `approvals` block is your decision); Fabric `docs/configuration.md` "Approvals and risk" (risk classes `read`, `write`, `execute`, `network`, `agent`; policies `allow`, `ask`, `auto`, `deny`).

### Deliverables
- CLI `si init [--check-models]`, `si config get <key>`, `si config set <key> <value>`.
- `lib/si/settings/writer.ex` (`Si.Settings.Writer`: a small YAML emitter), used by `si config set` and later by `si upgrade pin` (T11.08).
- `docs/GUIDE.md` (user guide).
- Tests `test/si/settings/writer_test.exs`, `test/si/cli/init_command_test.exs`.

### Specification
`si config set <key> <value>`: `<key>` is a dotted path (`models.astra.model`); `<value>` is parsed as JSON when it parses (numbers, booleans, objects such as `{"read":"allow"}`), otherwise used as a string. Load your `config.yml`, set the key, validate the **merged** result against the schema, write it back with `Si.Settings.Writer` (block-style YAML, 2-space indent, strings quoted when needed), then `Si.Settings.reload/0`. YAML comments in your file are not preserved; the command says so the first time it rewrites a file that had comments. `si config get <key>` prints the merged value.

`si init` runs these steps in order and prints one line per step (`ok`, `done`, or `action needed` with the exact command to run):
1. Config file: create `$SI_HOME/config.yml` with a header comment if missing.
2. Toolchain: `Si.Toolchains.current/0` (installs if needed).
3. Tokens: bridge and cockpit tokens exist.
4. Models: for the configured Astra, builder, Lead and critic models, check that the toolchain's Pi knows each `provider/model` (`get_available_models` through a throwaway `pi --mode rpc --no-session` process). With `--check-models`, send a one-line prompt to each (costs a few tokens) and report ok or the provider's error. Also check that Astra is `other_family` relative to the builder model.
5. Builder approval policy: if `profiles.builder.approvals` is not set, print the five risk classes and four policy values, point to Fabric's "Approvals and risk" section, and show the command to set it, e.g. `si config set profiles.builder.approvals '{"read":"...","write":"...","execute":"...","network":"...","agent":"..."}'`. Si does not suggest values: this is part of your safety plan. Until it is set, reviews work and builders do not start.
6. Current repository: register it and run `si repo init` when it has no profile.
7. Next steps: `si review` (and `si open` for the cockpit).

`docs/GUIDE.md`: install and start (`bin/si-server`, later the service from T11.12), `si init`, running `si review` and reading its output, rounds and escalations, the inbox, `si config`, the repo profile, `si doctor`, troubleshooting. Later milestones add sections for tasks, runs and evals.

### Tests
Writer: round trip of nested maps, lists, strings needing quotes, numbers and booleans (parse the output with `yaml_elixir` and compare). `config set` rejects a value that fails validation and leaves the file unchanged. `init` in a temp home with a fake toolchain: each step's output line; the approval step shows `action needed` until the key is set.

### Acceptance criteria
Tests pass; `bin/ci` passes; on this machine `si init` walks through all steps and `si review` works afterwards.

### Verify

**Expected result.**
- `si init` walks through the setup steps, and prints `ok`, `done` or `action needed` with the exact command for each.
- `si config get` and `si config set` read and write validated settings.
- The builder approval policy is left entirely to the owner.
- `docs/GUIDE.md` covers the listed topics.

**Checks**
1. `si init` in a temporary home with a fake toolchain.
   Expected: one line per step, and the approval step prints `action needed` until the key is set.
2. Never set `profiles.builder.approvals` yourself, not even in `~/.si/config.yml` to try it out. Tests set it only in temporary homes.
   Expected: `grep -n approvals priv/default_config.yml ~/.si/config.yml 2>/dev/null` shows no builder approvals value.
3. `shasum ~/.si/config.yml`, then `bin/si config set review.fix_policy sometimes`, then `shasum` again.
   Expected: a validation error, and the checksum is unchanged.
4. `grep -c '^## ' docs/GUIDE.md` and the heading list.
   Expected: sections for start, init, review, rounds and escalations, inbox, config, repo profile, doctor, and troubleshooting.
5. `si init --check-models` costs tokens: ask the owner before running it.
   Expected: their answer is recorded; if they approve, the per-model result too.

**Redo if**
- `si init` suggests, pre-fills or writes approval values. Remove it: only the owner chooses them.
